[3] 컴파일러 준비   ** 설치 불필요, 관리자 권한 불필요 **
--------------------------------------------------------------------
    C:\work\mingw64-portable.zip 을 탐색기에서 "압축 풀기" (1~2분)

    Git Bash 에서 — ★ **~/.bashrc 에 적는다. export 만 하면 새 창에서 사라진다.**
        cat >> ~/.bashrc <<'EOF'
export PATH="/c/work/mingw64/bin:$PATH"
export PYTHONIOENCODING=utf-8
EOF
        source ~/.bashrc

    ** 5시간 동안 터미널을 새로 여는 건 거의 확실하다. 그때 g++ 이 사라지고
       CP949 크래시가 되살아나면 원인을 찾느라 시간을 태운다. **

        # ★ --version 으로 확인하지 말 것. 실제로 컴파일해봐야 안다
        printf '#include <bits/stdc++.h>\nint main(){puts("ok");}' > /tmp/t.cpp
        g++ -O2 -std=gnu++20 /tmp/t.cpp -o /tmp/t.exe && /tmp/t.exe

        "ok" 가 찍혀야 진짜 준비된 것이다.

    ⚠️ **압축 해제가 끝나기 전에도 g++ --version 은 성공한다.**
       실측(2026-08-15): g++ 실행됨 → 그런데 cc1plus 없음 → 조금 뒤엔
       cc1plus 는 있는데 ctype.h 없음. **단계마다 "준비된 것처럼" 보인다.**
       --version 만 보고 [4] 로 넘어가면 거기서 시간을 태운다.

    ⚠️ **컴파일러는 USB 에만 있다 = 단일 실패점.**
       USB 가 인식 안 되면 C++ 자체가 불가능하다. 그 경우 즉시 운영진.

    ★ PYTHONIOENCODING 을 왜 넣나: 윈도우 콘솔이 CP949 라서
      ─ ⚠ ★ 같은 문자를 출력하면 파이썬이 **UnicodeEncodeError 로 죽는다.**
      계산을 다 해놓고 출력 한 줄에서 잃는다. 이 한 줄이 계통 전체를 없앤다.

    ※ 검증됨: WinLibs GCC 16.1.0 / x86_64 / thread model = posix
    ※ 대여 기기에 이미 컴파일러가 있으면 그걸 써도 된다.

      ⚠️ 문서에 오래 있던 **42.15초는 gcc 13.3.0 기준이라 17% 과대평가**였다.

      (2.33초 -> 1.80초. 한 번만 재고 "시간 초과다" 판단하면 틀린다)

    왜 재나: 빌려 쓰는 노트북 성능을 모른다. 이 값이 있어야
    "내 노트북에서 3초면 채점기에선 몇 초?" 를 계산할 수 있다.
    하나의 숫자로 대충 정해두면 안 된다 - 노트북뿐 아니라
    컴파일러에 따라서도 달라진다.

    ⚠️ **공식 컴파일 환경과 3가지가 다르다** (2026-08-24 확인, 공식 개발도구 페이지):
       - 표준: 우리 `-std=gnu++20` ↔ 공식 동일 (이미 맞춤). **C++17 은 공식 선택지에 없다.**
       - 컴파일러: 우리 MinGW g++ 16.1.0 ↔ 공식 gcc 14.2.0 (더 신버전이라 로컬만
         통과하는 코드가 나올 수 있다 — 이론상 위험, 실측으로는 문제 없었음)
       - 최적화: 공식은 `-DONLINE_JUDGE -DNYPC -march=native -mtune=native` 도 쓴다.
         우리 코드는 두 매크로를 참조하지 않아 무해. march=native 는 로컬 노트북엔
         일부러 안 넣는다(채점기 CPU와 다름).
         ★ 2026-08-24 실측: **속도 향상은 march=native 가 아니라 gcc14 자체**에서 왔다.
           gcc13+march 는 오히려 **느려졌다**(41초 -> 47초). march 를 성능 개선으로
           기대하지 말 것.
       상세: `archive/FINAL_ROUND_STRATEGY.md` §0.2, 공식 개발도구 페이지 참고.

             chmod 600 ~/.ssh/nypc2026-final.pem

           # chmod 가 안 먹으면(NTFS) PowerShell 에서:
           #   icacls "$env:USERPROFILE\.ssh\nypc2026-final.pem" /inheritance:r
           #   icacls "$env:USERPROFILE\.ssh\nypc2026-final.pem" /grant:r "$($env:USERNAME):(R)"

           아니라 순서를 뒤로 미루는 것이고, 제출 직후 바로 한다 **
      - 길을 정하면 흔들지 않기
      - 15:30 부터 새로 손대지 않기 / 15:50 코드 바꾼 마지막 제출
      - 항상 검증 통과본이 올라가 있게 유지. 이상하면 10초 만에 되돌린다
      - 빌드 후 반드시 파일 시각 확인 (낡은 실행파일로 검증하는 사고 방지)
      - 중간평가 입력을 받으면 바로 내려받아 실제 값으로 다시 맞추기
      - 설정 비교는 **입력마다 몇 번 이겼는지**로. run_batch 첫 줄의
        "작을수록/클수록 좋음" 이 문제와 맞는지 확인
        (점수가 클수록 좋은 문제면 --maximize 필수)
      - 입력이 몇 개 없을 때 내린 결론은 전부 임시. 중간평가마다 다시 확인
