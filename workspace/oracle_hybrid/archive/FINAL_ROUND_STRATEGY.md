- 대회 시간: **11:00–16:00 (5시간)** = 개발 시간.

## ☆☆ 본선 문제 구조 (규정 정독 결과) — 전략을 바꾸는 2가지

**본선 = 문제 1개, 챌린지 영역만** (예선의 스텝업 영역이 없음). "챌린지 영역 하나로만 구성" = 문제가 여러 개가 아니라 **영역이 하나**라는 뜻. 코드 1개를 제출하고, 그 코드가 **여러 입력(테스트케이스)에 대해 평가**된다.

| 평가 | 입력 | 점수 반영 |
|---|---|---|
| 사전평가 | 샘플 입력 (공개·고정) | ❌ 반영 안 됨 |
| 중간평가 | 주최측 **무작위 생성**, **참가자가 다운로드 가능** | ❌ 반영 안 됨 |
| 최종평가 | 주최측 **무작위 생성**(중간보다 많을 수 있음) | ✅ **이것만 점수** |

**① 하드코딩 레버 소멸** ⚠️ — 예선에서 통했던 "공개 입력에 최적화한 격자를 KNOWN_CASES로 내장" 전략은 **본선에 대응물이 없다.** 샘플 입력은 공개지만 최종평가에 반영되지 않고, 최종평가 입력은 무작위 생성이라 미리 알 수 없다. → **런타임 솔버 품질이 전부.** (구 §5의 "입력 공개면 오프라인 몰빵" 레버는 본선에선 무효.)

**② 중간평가 입력 다운로드 = 새 레버** 🔥 — 대회 시작 **1시간 후부터 중간평가 10회+**, 매번 **실제 채점에 쓰인 입력을 다운로드**할 수 있다. 답을 하드코딩할 순 없지만(최종 입력은 다름), **내가 추측한 생성기가 아니라 진짜 분포로 고정 seed 세트를 만들 수 있다.** 예선에서 공식 생성기를 역추정하느라 쓴 노력이 본선에선 불필요.
→ **타임라인 반영**: 12:00경 첫 중간평가 → 입력 확보 → 그때부터 **실제 분포로 튜닝**.

**제출 빈도**: 본선은 **10초에 1회** (예선 5분 2회) → 피드백 루프 고속화. 자주 제출해 순위 피드백을 받는 게 유리.

## ★ 추천 전략 (한눈에) — "안전장치 깔고 도전"

> **먼저 점수를 잠가두고, 그 위에서 과감하게 도전한다.** (전부 거는 게 아니다)

- **전반(11:00~13:00) = 점수 잠그기**: 일단 통과되는 제출을 바로 내고(0점 방지),
  확실한 방법으로 상위권 바닥을 만든다. **"확실히 되는 것"만.** 창의력은 아껴둔다.
- **후반(13:00~15:30) = 우승 도전**: 문제 성질을 파악한 뒤, 남는 시간 전부를
  "이 문제만의 구조"에 쓴다. **실패해도 앞에서 깔아둔 점수가 받쳐주니 과감하게.**
- **마무리**: **15:30부터 새로 손대지 않기** → **15:50 코드 바꾼 마지막 제출** → 이후 확인만.
  중요한 건 시각이 아니라 **상태**다 — *항상 검증 통과본이 올라가 있게 유지*하고,
  이상하면 10초 만에 되돌린다.

**핵심 안전장치**: 도전하는 방법은 **항상 따로 만들고**, 안전한 제출본을 절대 덮어쓰지 않는다.
정확한 채점기로 "안전한 것 vs 도전한 것" 중 더 좋은 걸 고르니 → **도전해도 손해가 없는 구조.**

**왜 이 방식인가**: 잘하는 80명 안이라 안정만으론 우승이 안 된다(도전이 필요) +
파이널까지 온 성과를 날리면 안 된다(점수 보호) → 둘 다 되는 유일한 방법.
**우승 확률 목표 15~20%, 실패해도 상위권 유지.**

**꼭 기억할 3가지**:
①사전 준비는 **코드가 아니라 환경 세팅 + 리허설**(채점기는 문제를 봐야 만들 수 있다)
②**중간평가 입력을 받는 즉시 실제 값으로 다시 맞추기**(본선에서 제일 큰 효과)
③**문제 성질 파악(12:00~12:30)을 감으로 때우지 말 것** — 예선 최대 실수가 그것이었다.
  ※ 단 11:30 제출이 아직 없으면 **제출이 먼저**다. 파악을 버리는 게 아니라
    순서를 뒤로 미루는 것이고, 제출 직후 바로 한다.

## 0. 두 개의 시계 (제일 먼저 분리)

| 시계 | 의미 | 대응 |
|---|---|---|
| **대회 5시간** | 나+Claude의 개발 시간 | §4 분단위 계획 |
| **실행 제한(미지)** | 프로그램이 입력 하나당 도는 한도(2초? 60초?) | §3 anytime 솔버 |

**11:00에 실행 제한을 제일 먼저 확인**한다. 이게 anytime 설계를 좌우한다.

> ⚠️ **현재 솔버의 치명적 공백**: 시계를 안 본다. 입력당 20~30초 고정 스윕이라 (a)제한이 짧으면 즉시 TLE 0점, (b)길면 남는 시간을 버림. **어떤 제한에서도 틀렸다. 최우선 수정 대상.**

### 0.1 실행 제한의 정확한 정의 (규정 원문)

- **CPU time 기준**이다. 벽시계가 아니다.
- **모든 스레드의 시간이 합산**된다 → 멀티스레드는 이득이 **0**이고 동기화 오버헤드만큼 **손해**.
- 메모리도 라이브러리·OS 할당분까지 합산. (우리 워크로드는 **7MB** 라 사실상 논외)

→ `skeleton.cpp` 는 **벽시계와 CPU time 을 둘 다 재고 먼저 닿는 쪽에서 끊는다.**
  단일스레드면 벽시계 ≥ CPU time 이라 벽시계만 봐도 안전하지만, 스레드를 쓰는 순간
  관계가 뒤집혀(**CPU ≈ N × 벽시계**) 타이머가 여유롭다고 믿는 사이 초과 판정이 난다.

### 0.2 ★ 채점기 실측 보정 (2026-08-05, 도쿄 c7a.2xlarge)

> ⚠️ **2026-08-24 재측정으로 이 절의 42.15초는 폐기됨.**
> 이 수치는 **gcc 13.3.0**(AMI 기본)으로 잰 값인데 공식 환경은 **gcc 14.2.0** 이다.
> 공식과 동일한 컴파일러·플래그로 EC2 c7a.2xlarge 에서 다시 재니 **35.1초**였다
> (기존 값은 **17% 과대평가**). 현재 유효한 앵커는 `START_HERE.txt [4]` 의 35.1초다.
> 부수 발견: 속도 향상은 `-march=native` 가 아니라 **gcc14 자체**에서 왔고,
> gcc13+march 조합은 오히려 느려졌다(41초 → 47초).


`AMD EPYC 9R14 @ 3700.163MHz / Ubuntu 24.04.4 / g++ 13.3.0` = **규정 명시 환경과 완전 일치**.

| 입력 | t3.micro | **c7a(채점기)** | 배율 |
|---|---|---|---|
| 공개1 | 63.5s | **42.15s** | 1.51× |
| 공개3 | 76.2s | **52.23s** | 1.46× |
| 공개4 | 107.2s | **70.77s** | 1.51× |

⚠️ **정정(2026-08-05): 상수 하나로 퉁칠 수 없다.**
포터블 g++ 16.1.0 으로 집 데스크탑에서 재니 **42.3s = 채점기(42.15s)와 사실상 동일**했다.
문서에 있던 "데스크탑 62s"는 다른 툴체인 기준이었다. **데스크탑에 ÷1.5 를 쓰면
시간을 1.5배 과소평가**해 예산을 초과한다. 배율은 기계뿐 아니라 **컴파일러에도** 좌우된다.

| 기준 | 컴파일러 | 공개1 | 채점기 대비 |
|---|---|---|---|
| t3.micro | g++ 13.3.0 | 63.5s | ÷1.5 |
| **c7a(채점기)** | g++ 13.3.0 | **42.15s** | 1.00 |
| 집 데스크탑 | g++ **16.1.0** | 42.3s | **≈1.00** |

**실무 규칙**: ①**c7a 에서 직접 측정**이 가장 안전(환산 불필요) ②다른 기기면
그 기기로 공개1 을 돌려 **42.15s 와 비교해 자기 배율**을 구한다 ③t3 대충 볼 때만 ÷1.5.
재측정 편차 1.7%.
cost 는 **윈도우 = t3.micro = c7a** 세 플랫폼 완전 일치(15,406 / 6,328 / 7,640, 전부 L=0).

#### 여기서 나오는 결론 — 예선 방식은 그대로 못 쓴다

> 예선 제출본은 **채점기에서 42~71초**. 시간제한이 넉넉했기에 성립한 구조다.

| 제한이 | 쓸 수 있는 비율 | 함의 |
|---|---|---|
| 2초 | **4.7%** | 전수 exact 평가 불가. 후보 수십 개가 한계 |
| 10초 | 24% | 여전히 선별 필수 |
| 60초+ | 대부분 | 예선 방식 유사 재사용 가능 |

→ **당일 11:00 에 실행 제한을 확인하는 순간이 노선 결정 지점.**
  제한이 짧으면 ①축소선별 게이트 필수 ②안전 기준안 확보의 가치가 급등
  (시간이 모자라도 유효한 답은 나가야 하므로).

## 0.5 🌐 외부 연산 자원 — **주최측이 전면 허용** (2026-08-04 확인)

운영본부 답변: **"질문 주신 내용 전부 가능합니다. 현장 와이파이 사용 시, 원격 접속 가능합니다. 개인 노트북 반입에 제한 사항이나 사전 점검 절차는 없습니다."**
→ 개인 PC 원격 접속(SSH), 클라우드(AWS/GCP) 모두 사용 가능.

### 무엇이 바뀌나

| | 전 | 후 |
|---|---|---|
| 대여 기기 성능 | 최대 리스크 | **거의 무관** (터미널이면 됨) |
| 로컬 스윕 속도 | 6코어 고정 | **128 물리코어**까지 (도쿄 할당량 승인) |
| 환경 불일치 | 윈도우↔리눅스 간극 | **채점기와 동일 환경에서 개발** |

### ⚠️ 반드시 지킬 선

> **"연산 분산"은 허용, "에이전트 병렬"은 여전히 금지.**

- ❌ 원격과 로컬에서 Claude 를 각각 띄우기 → **규정 위반**
- ✅ 원격에서 **검증기·솔버 같은 비-LLM 프로그램**을 병렬 실행 → 허용

**제출 코드는 여전히 1코어 CPU time.** 외부 연산은 *로컬 탐색·튜닝*만 빠르게 하지,
제출본의 실행시간에는 아무 도움이 안 된다. 단일스레드 설계는 그대로 유효.

### 구조: 로컬 주력 + 원격 보조

```
대여 기기(로컬)              AWS / 집 데스크탑(원격)
├ USB 툴체인으로 개발    ←→   ├ 대량 병렬 스윕
├ 빠른 빌드·제출              ├ 파라미터 탐색
└ WiFi 끊겨도 계속 가능       └ 채점기 동일 환경 타이밍 검증
```

WiFi 는 80명 공유다. **원격을 주력으로 삼으면 단일 장애점**이 된다.
USB 로컬 폴백이 이미 준비돼 있으므로, 그것을 기반에 두고 무거운 계산만 원격에 던진다.

```
1순위  AWS (채점기 동일 환경 + 코어)
2순위  집 데스크탑 SSH (무료)
3순위  로컬 USB 툴체인 (WiFi 무관)
```

### ★ 언제 띄우나 — **길을 정한 12:30 이후, 중간평가 입력이 있을 때**

트리거를 **시계가 아니라 사건**으로 잡는다. "로컬 스윕이 N분 넘으면"류의 규칙은
**순환**이다 — N분 걸리는지 알려면 먼저 돌려봐야 한다. 중간평가는 관찰 가능한 사건이다.

이 시점이 맞는 이유 3가지:
1. **입력 수가 뛰는 순간 = 스윕 비용이 뛰는 순간.** 3개→9개면 런 수가 3배
2. **판단이 필요 없다.** 중반의 흐려진 머리로 소요시간을 추정하지 않아도 된다
3. **시작 3~5분이 공짜로 숨는다** — 그동안 당신은 새 입력을 받고 분포를 보고 있다

그리고 리허설에서 **3개→9개로 늘리자 최선 설정이 뒤집혔다**(§0.6①).
입력이 늘어난 직후가 재검증이 가장 필요한 시점이고, 그게 정확히 중간평가다.

**절차**
- **12:00 (첫 중간평가)**: 입력만 받아둔다. **서버는 안 띄운다.**
  아직 길을 정하는 중이라, 버릴지 모르는 코드를 조정해봐야 의미가 없다.
- **12:30 이후 (길 확정)**: `allow-ip.sh` → `launch.sh sweep` → `sync.sh` → 스윕

⚠️ 첫 중간평가(12:00)는 길 확정(12:30)보다 **빠르다**. 이게 예외가 아니라 기본이다.

💸 **크기는 `sweep`(64코어)을 기본값으로.** 요금이 코어 수에 비례하고 처리량도 비례하므로
*같은 작업량이면 총비용은 같다* — 다른 건 **기다리는 시간**뿐이다. 그런데 128코어를
몇 시간 켜두는 건 그냥 낭비다(스윕은 몇 분이고 나머지는 유휴).

| 크기 | 시간당 | 언제 |
|---|---|---|
| **`sweep` (64코어)** | ~$4 | **기본.** 중간평가 때 띄워서 유지 |
| `max` (128코어) | ~$8 | 15:00 튜닝 구간의 대형 스윕에만 잠깐 |
| `free` (t3.micro) | $0 | 절차 연습용. 시간측정 부적합 |

teardown→relaunch 가 3~5분이라 갈아타는 부담이 없다. **전체 $10~15 선.**
관리할 것은 요금이 아니라 **끄는 습관**
(c7a.32xlarge 를 한 달 방치하면 **~$5,000**). 안전장치 3중: 자동 terminate / `teardown.sh` / Budgets.

⚠️ **코드를 고칠 때마다 `./sync.sh`.** AMI 안의 `run_batch.py` 는 결함 4건이 살아있는
낡은 사본이다. 실행 첫 줄의 `[run_batch <버전>]` 배너로 매번 확인할 것.

## 0.6 🧪 리허설에서 얻은 판단 규칙 (2026-08-05) ★

### ① 표본이 작으면 결론이 뒤집힌다 — **3번 재현됨**

| 표본 변화 | 무슨 일이 |
|---|---|
| 입력 3 → 9 | 최선 설정이 **뒤바뀜** (공개 세트에 없던 지형이 원인) |

→ **입력이 적을 때 내린 결론은 전부 잠정이다.** 중간평가를 받는 족족 재검증할 것.
→ 교훈은 "표본을 늘려라"가 아니라 **"내 세트에 없는 지형이 뭔지 물어라"**.

### ② 평균이 아니라 **승수**로 고른다

본선은 입력별 상대평가다. 실제로 평균 1위와 승수 1위가 **서로 다른 설정**이었다
(평균: PathFinder / 승수: 탐욕). 평균은 점수 스케일 큰 입력에 지배된다.
`run_batch.py` 가 승수를 1순위로 낸다. **평균은 참고만.**

### ③ 하한 — **왜 느슨해지는지 알고 써야 한다** ★★

하한은 **제약을 버려서** 만든다(버리면 최적해가 나빠질 수 없으므로 하한이 된다).
문제는 **무엇을 버렸는가**다.

> 🔑 **결합(coupling) 제약을 버리면 "각자 최적의 합"이 나온다.
>    그런데 결합이 곧 그 문제의 난이도인 경우가 많다.
>    그러면 그 하한은 문제의 본질을 통째로 버린 값이라 도달 불가능하다.**

**같은 실패를 두 번 했다:**

| | 버린 결합 | 결과 |
|---|---|---|
| 예선 씨앗운반 | 2D 트리 임베딩 | LP 로 E=0 증명 → **9일 동안 못 만듦** |
| 리허설 배선 | 배선 비겹침 | 하한 1,176 → **22배 격차가 허수** |

**당일 규칙**
1. 하한이 **"각자 최적의 합" 류면**, 결합이 강한 문제에선 **무의미하다고 미리 가정**한다
2. 하한은 격차 측정보다 **항별 분해**에 쓴다 — 배수는 지표가 아니다
   (벌점이 단위비용보다 크면 몇 건만 놓쳐도 폭발한다. 리허설: "14.8배"의 정체가 3쌍 미연결)
3. 하한이 **유용한 건 오히려 "가까울 때"** — 근접했다면 *더 짜낼 게 없다*는 확실한 신호이고,
   그건 **다른 데 시간을 쓰라는 판단**을 준다
4. 도달 가능성 검사(자원 합 vs 가용)는 **필요조건일 뿐**. 자원이 남아도 기하적으로
   불가능할 수 있다 (리허설: 점유율 32%인데 격차 14.8배)

방법의 본보기: `bound_example.py` — ①완화 하한 ②신뢰도 검사 ③**항별 분해** 3단.

밀도 정렬(−16%) / 단자 회피 강·약(무익) / 하한(허수) / 스팟 AZ 최적화(용량 없어 실패).
**5번 다 측정이 잡았다.**

### 이번에 통한 것 (자산)

- **"행=목표 굴" 삼각 버스**: 어느 열에서 떨궈도 굴 j로 배송 → 분할영역 가로배선 제거. 배치 난이도를 결정적으로 낮춤.

- comb 구조적 약점: caterpillar가 **항상 ⌈A/2⌉를 첫 조각**으로 흘려서, 한 원천에 질량이 쏠리면 첫 조각이 모든 B_j보다 커져 E 폭발(고M 밴드에서 v5에 20~25% 밀림, 진 5/35가 전부 이 계열).

## 2. 핵심 전환: "정답을 만들지 말고, 기계가 정답을 찾을 판을 만들어라"

표준 휴리스틱 우승 공식 = **점진적 개선(탐욕 시작) + 로컬탐색/SA + 시간관리 + 시각화.** 우리에게 없는 조각은 SA와 시간관리뿐. 이번 자산(오라클) 위에 얹으면 된다.

**최종 형태 = multi-start SA + exact 오라클:**
1. 여러 구성으로 **다양한 시작점** 생성 (whole/comb/…)
2. 각 시작점을 **해 자체 변이 SA**로 제한시간까지 개선 (목적함수 = 내장 exact 시뮬)
3. **exact 평가로 최선 선택** (오라클)

대부분 참가자는 SA 한 줄기만 돌린다. 다양한 시작점 + 정확 선택이 우리 우위.

> **핵심: 사람은 "표현 + 변이 집합"만 설계한다(여기가 진짜 창의력). 구조는 기계가 찾는다.**
> 손설계는 내 머리가 상한이지만, 탐색은 시간·코어가 상한 → 상방이 열려 있다.

### 2.1 멀티 가설 반복 생성 (Inference-time Scaling) — 오라클의 정식 확장
ALE-Agent(사카나 AI)식 상위권 공식 = **수백 개 서로 다른 전략을 자동 생성 → 전부 exact 테스트 → 최선 선택.** 우리 오라클이 바로 이것의 씨앗(여러 후보→실측→최선). 차이는 (1)손설계 몇 개 → **AI가 다양하게 대량 생성**, (2)**Claude가 그 생성 주체**.
- **태도 전환: 한 계열(comb) 깊게 파지 말고 여러 계열을 얕고 넓게 찍어낸다.** 이번의 최대 실수가 한 계열 몰빵.
- 5시간 = **추론시간 확장**으로 재정의: Claude가 계속 생성기·변이집합·평가가중치 가설을 찍고 → 고정 seed로 채점 → 실험로그로 먹히는 계열 식별 → 거기에 SA/튜닝 집중 → anytime이 계산시간을 꽉 채움.
- ⚠️ **냉정히: 이 엔진은 "안정적 상위권"용이지 그 자체로 1등 보장 아님**(ALE-Agent도 12위권, 우승 아님). → **오라클로 상위권 보험을 깔고, 남는 시간에 "남들이 못 본 구조" 한 방을 베팅**하는 순서(§2)가 정답.

예선 오라클의 병목: **모든 후보를 exact 시뮬**했다(361후보 = 28초). 그래서 후보 수가 곧 시간이었다.
→ **싼 근사 게이트를 앞에 두면** 같은 시간에 훨씬 많은 후보를 볼 수 있다.

> 🔴 **경고 (2026-08-05 리허설로 드러남): ④ 축소선별은 조건부 도구다.**
> 이 파이프라인은 **"평가가 생성보다 비싸다"**를 전제한다. 예선(씨앗운반)에선
> 맞았지만 — exact 시뮬이 지배적이었다 — **리허설 2문제 모두 정반대였다.**
> 생성이 지배적이고 평가는 즉시라서, 축소선별을 넣을 자리가 없었다.
> 스켈레톤 자체 데모에서도 `-DNO_SCREEN` 쪽이 나았다.
>
> **즉 이 파이프라인은 지금까지 딱 한 문제(예선)에서만 검증된 구조다.**
> → **11:00 에 먼저 판정할 것: 생성이 비싼가, 평가가 비싼가?**
>   - 평가가 비싸다 → 축소선별 게이트 O (아래 예산표대로)
>   - 생성이 비싸다 → **④⑤를 버리고** "생성 → 즉시 정확평가"를 한 덩어리로 반복
>   판정법: 후보 1개 만드는 시간 vs 1개 평가하는 시간을 각각 재본다(수 분).

```
① 입력 특징 몇 개 추출        (당일 문제 보고 결정)
② 안전 기준안 즉시 생성        ← 항상 유효. 이후 후보는 "실측이 더 낮을 때만" 교체
③ 특징에 맞는 후보군 생성      (가족 2개: 안전형 1 + 공격형 1)
④ 축소 시뮬(1/4·1/8)로 선별   ★ 신규 — 오라클 병목 해소
⑤ 상위 2~4개만 정확 시뮬
⑥ 검증된 최선 출력
        ↑ 각 단계에 시간을 강제 배분(아래)
```

### 단계별 강제 시간 예산 (제한 2초 예시 — 실제 제한은 11:00에 확인)
| 구간 | 할 일 |
|---|---|
| 0.00~0.15 | 특징 계산 · **안전 답안 확보** |
| 0.15~0.60 | 후보 생성 + 정적 평가 |
| 0.60~1.10 | **축소 시뮬로 선별** |
| 1.10~1.75 | 상위 후보 **정확 시뮬** |
| 1.75~ | 탐색 종료 · 출력 · 안전 여유 |

⚠️ **입력이 쉬워 보인다고 정확 시뮬 후보 수를 늘리지 말 것.** 입력 크기와 무관하게 단계별 시간을 강제 보장한다.
(예선 저M 약세의 원인을 "쉬워 보이는 입력에 시간 과소비"로 추정했었으나 **검증된 바 없다.**

**이 추정을 근거로 삼지는 말 것.**)

### 하드코딩 조건 → 특징 기반 라우팅
예선 코드의 `C==6 && M<=376195` 류는 **명백한 과적합**이었다. 조건을 **입력에서 계산한 특징**으로 바꾼다.
단, **5시간에는 결정트리·점수식은 사치** — **`if` 2~3줄로 시작**하고 데이터가 쌓이면 조건을 붙인다.

### ⚠️ 상대평가에서 꼬리 위험의 정체 (절대비용 기준과 다름)
`Score = 10⁶ × (1 − 우리보다잘한비율)` 이라 **입력당 점수에 상한이 있다.** 비용이 좀 나빠도 0점이 아니라 부분점수다.
실제로 예선 최종평가는 **최강 12.9% ~ 최약 16.0%, 편차 3.1%p**로 꽤 균일했다(§1.5).
→ **진짜 꼬리 위험은 "비용이 나쁜 것"이 아니라 "무효·TLE·실격"** — 그건 그 입력 10⁶점을 통째로 날린다.

**목적함수 우선순위**
```
1순위: 무효/TLE 0건            (하드 제약 — 무조건)
2순위: 최악 입력의 상대점수
3순위: 평균 상대점수
```
평균이 조금 좋아지는 대신 **무효 위험이 오르는 후보는 대표안으로 쓰지 않는다.**

### 로깅 (싸고 효과 큼)
입력마다 CSV 한 줄: `문제파라미터 / 특징 / 선택된 family / 하이퍼(depth·cap·seed) /
정적평가 / 축소평가 / 정확평가(비용·유효성) / 후보수 / 생성시간 / 시뮬시간 / 최종비용`
→ "C=9 중간 M이 약하다" 같은 뭉뚱그린 진단 대신 **"어떤 특징 조합에서 어떤 family가 안 뽑혔나"** 를 찾을 수 있다.

### 검증 세트 — 합성 분할보다 **중간평가 실제 입력**
학습/검증/봉인 3분할은 원칙은 옳지만 5시간엔 과하다. 본선엔 더 좋은 게 있다:
**중간평가 입력을 다운로드**할 수 있다(1시간 후부터 10회+). 합성보다 **진짜 분포**가 낫다.
→ 고정 seed 세트 하나 + **중간평가 입력 누적** + 무효 0건 게이트로 충분.

### ⚠️ 문제 특정 지식은 전이되지 않는다
포트폴리오·축소선별·강제예산·로깅 같은 **메타 구조만 전이**된다.
`M/sum(A)`, majorization residual, CMW·tri·twin·dual·v23·comb 같은 **특징 목록과 후보 가족 이름은
씨앗 운반 전용**이다. 본선 후보 가족은 **당일 문제를 보고** 만든다.

## 5. 관통 레버 (전 노선 공통, 빠름)

- **목적함수 해부 먼저.** 이번 `2^(R-C)+max(E,D)+T·L`: `max(E,D)`는 작은 쪽 줄이면 이득 0(→D를 팔아 E를 사야), `2^(R-C)`는 R-C~12 넘으면 무의미한 절벽. **병목 항에만 자원 투입.** 두 항 균형 맞추려다 손해 보는 참가자 많음.
- ~~**메타 규칙 = 최대 레버.** 입력 공개면 일반 솔버 무의미 → 답을 하드코딩~~
  🔴 **본선에선 무효다.** 최종평가 입력은 무작위 생성이라 하드코딩할 대상이 없다(맨 앞 §☆☆ ①).
  예선에서 통했던 레버라 습관적으로 손이 갈 수 있는데, **그쪽에 시간을 쓰면 그대로 손실**이다.
  본선의 대응물은 **중간평가 입력을 받아 실제 분포로 튜닝**하는 것이지 답 하드코딩이 아니다.
- **조합 코어는 정확 솔버로 환원.** 배정/흐름/스케줄링으로 보고 LP/MILP/DP/매칭으로 정확히 풀고, 창의력은 "실현 층"에만. (이번 핵심이 수송문제였음.)
- **유효성 게이트 최우선.** L>0=즉사류 규칙은 대부분 있음. 제출 전 무조건 로컬 검증.
- **오버피팅 방지 = 고정 세트로 판단.** 튜닝·후보 채택은 **단일 케이스가 아니라 세트 전체**로.
  ⚠️ 단 **세트 크기 20~50 은 충분조건이 아니다** — 리허설에서 3→9 에서도, 9→100 에서도
  결론이 뒤집혔다(§0.6 ①). **중간평가를 받는 족족 세트에 누적**하고, 판단은 **승수**로 한다. **단일 케이스 점수로 파라미터를 만지지 않는다**(이번에 max-half·C5 컷오프에서 실제로 몇 케이스 올리다 전체 회귀 목격). 마라톤 전형 실패 = "몇 seed 올리다 분포에서 손해".
- **실험 로그를 남긴다.** 제출/설정 변경마다 한 줄 append: `{시각, 커밋/설정, seed세트 점수(평균·중앙·최악), L, 비고}`. 이번엔 이걸 대화로만 해서 재실행·낡은바이너리 검증 사고가 났다. "어느 방향이 실제로 효과 있었나"를 데이터로 봐야 헛발질을 막는다.

**결정적**: 당일 최대 시간 먹는 구간(11:30–12:00 **exact 채점기 작성**)이 정확히 **미리 못 만드는 부분**. 채점기는 문제 규칙 그 자체라 문제를 봐야 쓸 수 있다. 나머지는 15~30줄이라 당일 몇 분이면 씀. → **풀 하네스를 미리 만들어도 절약 30~40분, 문제가 예상 밖이면 그마저 줄어든다.**
(문제를 모르는 채 정교한 하네스에 몰빵 = 예선에서 E=0 트리에 며칠 태운 것과 **같은 실패 패턴**.)

### 6.2 실제 우선순위 (코드가 아니다)

1. **환경 세팅 — 필수, 협상 불가.** 컴파일러·git·gh·python, **권한 사전 허용**. 문제와 100% 무관하고 여기서 사고 나면 치명적(이번 세션에서도 컴파일러 탐색·exe 잠김·낡은 바이너리 검증으로 여러 번 시간 손실). → `PRE_CONTEST_SETUP.md`
2. ✅ **리허설 — 축약 2회 완료**(최대화·최소화). 수확은 `REHEARSAL_FINDINGS.md`.
   남은 건 *5시간 완주*뿐이고, 그건 후반 피로 측정용이라 우선순위가 낮다.
   (원문) **5시간 모의 리허설 1회 — 가장 가치 큼.** 얻는 건 코드가 아니라 **흐름·리듬·사고 발견**: 11:30 마감 체감, **크레딧 실측**($30인지 $80인지), **Fable 5 15분 지연 체감**, 환경 사고 미리 터뜨리기.
3. **얇은 스켈레톤 — 선택(시간 남으면).** 150줄: 입력파싱 스텁 / `struct Candidate` / `evaluate()` 스텁 / 시간예산 루프 / 병렬평가 / 최선선택+출력. 당일 함수 3개만 채움. 20~40분 절약.
4. USB 굽기 · 상태→HTML/ASCII 덤프 · git push.
5. ~~풀 하네스 제작~~ → **불필요.**

### 6.3 제출 코드 필수 사항 (당일 작성, 잊지 말 것)
- **단일 스레드 anytime** (채점 1코어·스레드 시간 합산):
  ```cpp
  auto t0=now(); double budget=0.95*LIMIT;   // LIMIT = 문제의 실행 시간제한
  while(elapsed()<budget){ ...개선... }      // best 항상 유효, 단일 스레드
  ```
- **오라클 선택 루프**(안전빵 vs 베팅 자동선택). 예선 코드의 **스레드 병렬 평가는 제출본에서 제거**(1코어라 손해). **로컬 검증·스윕은 멀티코어 유지.**

### 6.4 하방은 코드가 아니라 규율로 잠근다
1. **baseline은 하네스 없이 제출 가능**(greedy/random) → 11:30 유효제출로 0점 방지.
2. **지형 판별(§3)이 SA 먹히는지 30분에 검증** → 안 먹히면 즉시 구성+오라클로 갈아탐.
3. 채점기만 서면 오라클·배치는 당일 몇 분 안에 붙는다.
→ **하네스가 없어도 대회는 돌아간다.** 없으면 안 되는 건 **환경과 규율**.

### 6.5.0 ★ 과금 경로 — **Pro 구독(앱)으로 확정** (2026-08-15 결정)

Claude Code 를 평소처럼 로그인해서 쓴다. **API 키는 쓰지 않는다.**
(API 크레딧 경로는 5시간 한도가 없다는 장점이 있으나, 인증 전환에 재시작이 필요하고
대화 컨텍스트가 날아가는 비용이 있어 채택하지 않았다.)

**따라서 5시간 롤링 한도가 그대로 걸린다.**

**얼마나 위험한가**: 2026-08-12 세션에서 5시간 작업에 **한도의 76%**를 썼다.
대회도 5시간이니 **여유가 24%**다. 확정된 위험이 아니라 "대회 강도가 그날보다 높으면"이다.
→ 목표는 단순하다. **소비를 20~25% 줄이면 편안해진다.**

#### 여유를 만드는 3가지

**① 대회 당일 아침에 Claude 를 쓰지 않는다** — 가장 큰 레버.
5시간 **롤링**이라 06:00 에 쓴 것이 11:00 창에 남아 있다. 아침을 비우면 창 전체가 대회 몫이 된다.

**② 소비 레버 (효과순)**
- **파일 통째 재작성 금지** → 부분 수정. (10k 출력 = 일반 턴의 5~7배)
- **단순 작업은 effort 낮추기** — Opus 5 는 low/medium 이 유난히 강하다
- **긴 파일 반복 읽기 지양** — 한 번 읽으면 캐시에 남는다

**③ 폴백을 미리 정해둔다** — 아래.

#### ★ 진짜 보험: "Claude 없이 계속하기" 카드

한도에 걸려도 **대회는 멈추지 않는다.** 도구가 전부 CLI 이기 때문이다.

```bash
SINGLE=1 ./build.sh submission.cpp sol      # 빌드
./judge.exe input.txt output.txt            # 채점
python run_batch.py --inputs "inputs/*.txt" ...   # 스윕 (problem-agnostic)
```

`run_batch.py` 는 Claude 없이 그대로 돈다. 한도에 걸리면 **직접 스윕을 돌리고
승수를 읽어 최선 설정을 고르면 된다.** 새 코드를 못 쓸 뿐 튜닝은 계속된다.

> ⚠️ **준비물: 당일 자기 문제에 맞는 `run_batch.py` 명령줄 한 줄을 메모장에 복사해둘 것.**
> 한도에 걸린 뒤에 명령어를 재구성하려 하면 그때가 진짜 위기다.

그리고 철칙 3(**항상 known-good 이 제출된 상태 유지**)이 여기서 진가를 발휘한다.
