# ☁️ AWS 작업 인스턴스 — 채점 환경과 동일한 곳에서 개발·검증

> **왜 AWS인가**: 코어가 많아서가 아니라, 채점기가
> **`c7a.2xlarge` / Ubuntu 24.04 / AMD EPYC 3.7GHz** 이기 때문이다.
> 같은 인스턴스를 빌리면 **실행시간 측정이 채점기와 일치**한다.
> 1코어 시간제한 문제에서 이건 결정적이다 — 내 PC 기준으로 시간예산을
> 맞추면 채점기에서 어긋난다.
>
> 부수 효과: 지금까지 윈도우(MSVC/MinGW)에서만 빌드했는데, 채점기는
> 리눅스 g++ 다. 그 간극도 같이 없앤다.

## 1. 준비 (한 번만, 대회 전에)

### 1-1. AWS CLI 설치

```bash
winget install -e --id Amazon.AWSCLI
```

설치 후 **터미널을 새로 열고** 확인:

```bash
aws --version
```

### 1-2. 계정 · IAM 사용자

1. https://aws.amazon.com 에서 **계정 생성** (결제수단 필요)
2. 루트 계정으로 상시 작업하지 말 것 → **IAM 사용자** 생성
   - 권한: 연습용이면 `AmazonEC2FullAccess` + `AmazonSSMReadOnlyAccess`
3. 그 사용자의 **액세스 키** 발급 → 화면에 뜰 때 복사 (다시 못 봄)

### 1-3. 자격증명 등록

```bash
aws configure
```

| 물어보는 것 | 넣을 값 |
|---|---|
| Access Key ID | 발급받은 키 |
| Secret Access Key | 발급받은 시크릿 |
| Default region | **`ap-northeast-1`** (도쿄 — 서울엔 c7a 가 없다) |
| Default output | `json` |

확인:

```bash
aws sts get-caller-identity
```

### 1-4. 키페어 (SSH 접속용)

콘솔 → EC2 → **키 페어** → 생성
- 이름: `nypc2026`
- 형식: `.pem`

받은 파일을 `~/.ssh/nypc2026.pem` 으로 옮기고 권한 조정:

```bash
mkdir -p ~/.ssh && mv ~/Downloads/nypc2026.pem ~/.ssh/ && chmod 600 ~/.ssh/nypc2026.pem
```

### 1-5. 예산 알림 (권장)

콘솔 → **Billing → Budgets** → 월 예산(예: $30) + 임계치 알림.
켜두고 잊는 사고를 막는 **두 번째** 안전장치다.

## 2. 사용법

```bash
cd /d/tools/seed_transport/aws

./launch.sh          # 채점기와 동일 사양(c7a.2xlarge, 8코어)
./launch.sh sweep    # 대량 탐색용(c7a.16xlarge, 64코어)
./launch.sh max      # 할당량 상한(c7a.32xlarge, 128코어)
./launch.sh free     # 무료 t3.micro (절차 연습용)
./sync.sh            # 로컬 코드 → 인스턴스
./verify.sh          # 리허설: 빌드 → 공개1 → 채점 (cost 15,406 확인)
./connect.sh         # 셸 접속
./connect.sh "명령"  # 한 줄 실행
./fetch.sh '~/work/*.csv'   # 결과 회수
./status.sh          # 지금 뭐가 켜져 있나
./teardown.sh        # ★ 삭제 (과금 정지)
```

### ★ 준비된 이미지 (AMI) — 부팅 1분

`ami-05e1dddb66c14c6a7` (`nypc2026-ready-20260805-1359`, 도쿄)에
**g++ 13.3 · python3 · 레포 · `run_batch.py` · 빌드된 채점기**가 전부 들어 있다.
`launch.sh` 가 기본으로 이걸 쓰므로 **부팅하면 바로 작업 가능**(툴체인 설치 2~4분 절약).

- 검증됨(2026-08-05): 부팅 1분 → 즉시 공개1 실행 → `cost=15406` 재현.
- 기본 Ubuntu 로 띄우려면 `BASE=1 ./launch.sh`
- 이미지가 지워졌으면 **자동으로 기본 Ubuntu 로 폴백**한다(경고 출력).
- AMI 는 EBS 스냅샷을 물고 있어 월 $1 남짓 든다. 대회 끝나면 이미지+스냅샷 삭제.

> 🔴 **AMI 안의 코드는 절대 쓰지 말 것. 항상 `./sync.sh` 로 덮어쓴다.**
> 이미지를 구운 시점의 사본이라 **낡았다.** 실제로 검증 중 AMI 내장 `run_batch.py` 가
> 결함 4건(최대화 오선택·파일경합·사유누락·평균기준)이 그대로인 구버전이었다.
> **AMI 의 가치는 툴체인(g++·python)이지 코드가 아니다.**
> `run_batch.py` 는 시작 시 `[run_batch <버전>]` 을 찍으니 낡은 사본이면 바로 보인다.

첫 흐름은 이 순서 그대로:

```bash
./launch.sh && sleep 180 && ./sync.sh && ./verify.sh
```

## 2.5 🧮 인스턴스 크기 고르기 (도쿄 할당량 = **128 vCPU**, 2026-08-05 증액 승인)

**C7a 는 SMT 가 꺼져 있어 `1 vCPU = 물리 코어 1개`다.** 보통 클라우드의 "32 vCPU"는
16코어×2스레드지만 C7a 는 진짜 32코어다. 단일스레드 솔버를 여러 개 돌리는
우리 작업에는 이 차이가 그대로 성능으로 온다.

| 명령 | 타입 | 코어 | 집 데스크탑(6코어) 대비 | 쓸 때 |
|---|---|---|---|---|
| `./launch.sh free` | t3.micro | 2 | — | 절차 연습 (무료) |
| `./launch.sh` | c7a.2xlarge | 8 | ~1.4× | 채점기 동일 환경 확인 |
| `./launch.sh sweep` | c7a.16xlarge | 64 | **~11×** | 일반 스윕 |
| `./launch.sh max` | c7a.32xlarge | 128 | **~21×** | 대량 스윕 |

**크기는 스윕 규모에 맞춘다.** 요금이 코어 수에 거의 비례하므로
*같은 양의 작업이면 큰 인스턴스나 작은 인스턴스나 총비용은 비슷*하고
큰 쪽이 먼저 끝난다 → **대회 중엔 벽시계가 희소 자원이니 크게 쓰는 게 이득**.
단 인스턴스 시작에 2~4분이 드니, 스윕이 그보다 짧으면 키울 이유가 없다.

> `run_batch.py` 는 병렬도 기본값이 `nproc` 이라 **인스턴스 크기에 자동 적응**한다.
> 코어 수에 맞춰 명령을 고칠 필요가 없다.

## 3. 💸 비용 — 안전장치 3중

정확한 요금은 [EC2 요금표](https://aws.amazon.com/ec2/pricing/on-demand/)에서
**`ap-northeast-1`(도쿄)** / `c7a` 를 직접 확인하세요. 콘솔의 인스턴스 유형 선택
화면에도 시간당 요금이 표시됩니다.

**대략의 규모** (us-east-1 c7a.2xlarge $0.411/h 기준 환산 — **추정치**):

| 타입 | 시간당(추정) | 당일 3시간 |
|---|---|---|
| c7a.2xlarge (8코어) | ~$0.45 | ~$1.4 |
| c7a.16xlarge (64) | ~$3.6 | ~$11 |
| c7a.32xlarge (128) | ~$7.2 | ~$22 |

**크게 쓰는 게 항상 이득은 아니다.** 요금도 처리량도 코어 수에 비례하므로
*같은 작업량이면 총비용은 같고*, 다른 건 **기다리는 시간**뿐이다.
그런데 **초반엔 기다릴 게 없다** — 입력 3개면 로컬로 8초다.

| 시간대 | 입력 수 | 쓸 것 | 비용 |
|---|---|---|---|
| 초반 | 3(샘플) | **로컬만** | $0 |
| 중반 | 10~30 | 로컬 또는 무료 t3.micro | $0 |
| 후반 | 40~100 | `./launch.sh sweep`(64코어) | ~$3 |
| 대형 스윕 | 100+ | `./launch.sh max`(128코어) 잠깐 | ~$2 |

**전체 $5~10** 이면 충분합니다.

> 💣 **c7a.32xlarge 를 한 달 방치하면 ~$5,000.**
> 코어를 16배로 키운 만큼 방치 비용도 16배가 됐습니다.
> **끄는 습관이 전보다 훨씬 중요해졌습니다.**

문제는 요금이 아니라 **켜둔 채 잊는 것**입니다.

| 안전장치 | 내용 |
|---|---|
| ① 인스턴스 자동 종료 | 부팅 후 `AUTO_SHUTDOWN_MIN`(기본 480분) 뒤 자동 terminate |
| ② `./teardown.sh` | 작업 끝나면 즉시 실행 — **습관화** |
| ③ Budgets 알림 | 콘솔에서 설정 (1-5) |

- shutdown 동작이 **terminate** 라서 자동 종료 = 인스턴스 삭제 = 과금 0.
  대신 **인스턴스 안의 데이터도 사라진다** → 결과는 `./fetch.sh` 로 미리 회수.
- ⚠️ **큰 타입(`sweep`/`max`)은 스윕이 끝나면 즉시 내린다.**
  스윕 돌려놓고 다른 일 하다 잊는 게 가장 흔한 사고 패턴이다.
- 큰 타입엔 자동 종료를 짧게: `AUTO_SHUTDOWN_MIN=90 ./launch.sh max`

## 3.5 ❌ 스팟 인스턴스 — 시도했다 **버렸다** (2026-08-05)

스팟이 온디맨드의 1/3~1/2로 싸고(관측: c7a.32xlarge 도쿄 $1.71~2.99/시간),
배치 스윕은 끊겨도 다시 돌리면 그만이라 잘 맞아 보였다. **구현해봤고, 걷어냈다.**

| 걸린 문제 | 내용 |
|---|---|
| **최저가 AZ 에 물량이 없다** | 가장 싼 `ap-northeast-1d`($1.307)에 고정했더니 `InsufficientInstanceCapacity`. **싼 이유가 물량이 없어서**였다 |
| 폴백 로직이 필요해짐 | AZ 해제 재시도 → 온디맨드 재시도 … 분기가 늘어남 |
| `set -e` 함정 | `OUT="$(cmd)"` 가 실패하면 폴백 검사에 **도달하기 전에 스크립트가 죽는다** |

**결론: 대회 당일에 쓸 물건이 아니다.**
- 절감액은 전체 $5~8 중 몇 달러 — **판돈이 작다**
- 반면 실패 모드가 여럿이고, **당일 처음 겪으면 시간을 태운다**
- 반쯤 만든 채로 두는 게 가장 위험해서 **코드를 완전히 제거**했다

> 원칙: **대회 당일 도구에는 "돈은 아끼지만 실패 모드가 느는" 최적화를 넣지 않는다.**
> 이번 준비에서 나온 사고 대부분이 그런 종류였다.

## 4.5 ✅ 검증 기록 (2026-08-05)

**t3.micro / Ubuntu 24.04.4 LTS / g++ 13.3.0 / 단일스레드(`SINGLE=1`)**

| 입력 | 윈도우(MSVC·MinGW) | EC2 리눅스 g++ | L | 실행시간 | 메모리 |
|---|---|---|---|---|---|
| 공개1 | 15,406 | **15,406** ✅ | 0 | 63.5s | 5.9MB |
| 공개3 | 6,328 | **6,328** ✅ | 0 | 76.2s | 5.9MB |
| 공개4 | 7,640 | **7,640** ✅ | 0 | 107.2s | 7.3MB |

확인된 것:
- **크로스플랫폼 재현 완료** — 윈도우와 리눅스 g++ 결과가 비트 단위로 같다.
  이제 리눅스에서 개발해도 결과가 달라질 걱정이 없다.
- **메모리는 논외** — 최대 7MB. 램 1GB짜리에서도 남아돈다.
- 전체 절차(launch → ssh → sync → build → run → judge) 실측 검증됨.

### 채점기 동일 하드웨어 실측 ★

**c7a.2xlarge / 도쿄 / `AMD EPYC 9R14 @ 3700.163 MHz` / Ubuntu 24.04.4 / g++ 13.3.0**
= 규정에 적힌 채점 환경과 **완전 일치**.

| 입력 | t3.micro | **c7a.2xlarge** | 배율 | cost |
|---|---|---|---|---|
| 공개1 | 63.5s | **42.15s** | 1.51× | 15,406 ✅ |
| 공개3 | 76.2s | **52.23s** | 1.46× | 6,328 ✅ |
| 공개4 | 107.2s | **70.77s** | 1.51× | 7,640 ✅ |

재측정 편차 1.7%(42.15→42.85s) — 고정 성능이라 안정적.

#### 🔑 보정 — ⚠️ **상수 하나로 퉁칠 수 없다** (2026-08-05 정정)

| 기준 | 컴파일러 | 공개1 | 채점기 대비 |
|---|---|---|---|
| t3.micro | g++ 13.3.0 | 63.5s | **÷1.5** |
| **c7a (채점기)** | g++ 13.3.0 | **42.15s** | 1.00 |
| 집 데스크탑(i5-9400F) | **g++ 16.1.0** (포터블) | **42.3s** | **≈1.00** |

- t3.micro 배율 1.5 는 **같은 컴파일러로 3개 입력에서 일관**(1.46~1.51) → 신뢰 가능.
- ❌ **정정**: "집 데스크탑도 1.47×" 는 틀렸다. 그 62s 기록은 다른 툴체인 기준이었고,
  포터블 g++ 16.1.0 으로 재니 **42.3s = 채점기와 사실상 동일**하다.
  → 데스크탑에 ÷1.5 를 적용하면 **시간을 1.5배 과소평가**해 예산을 초과한다.
- 즉 배율은 **기계뿐 아니라 컴파일러에도 좌우된다.** 대여 기기는 미지수다.

**실무 규칙**
1. 가장 안전 — **c7a 에서 직접 개발·측정**. 환산 자체가 불필요.
2. 다른 기기를 쓴다면 **그 기기에서 기준 워크로드를 한 번 재서** 자기 배율을 구할 것.
   (공개1 을 돌려 42.15s 와 비교하면 바로 나온다)
3. 무료 t3.micro 로 대충 볼 때만 ÷1.5.

#### ⚠️ 여기서 나온 전략적 함의

예선 제출본은 **채점기에서 42~71초** 걸린다. 예선 시간제한이 넉넉했기에
성립한 구조라는 뜻이다. **본선 시간제한이 짧으면(2~10초) 이 방식은 못 쓴다** —
후보를 전부 exact 평가하므로 시간에 정비례한다.
→ 당일 **문제의 시간제한을 확인하는 순간이 노선 결정 지점**이고,
   `skeleton.cpp` 의 anytime + 단계별 강제예산 설계가 그 대비다.

## 4.6 ⚠️ 리전 함정 — **서울에 c7a 가 없다**

2026-08-05 확인. 콘솔에서 아무리 찾아도 `c7a.2xlarge` 가 안 나온다.

| 선택지 | 리전 | CPU | 비고 |
|---|---|---|---|
| **c7a.2xlarge** | **도쿄 `ap-northeast-1`** | EPYC 9R14 3.7GHz | ✅ 채점기와 동일. **실측에 사용** |
| m7a.2xlarge | 서울 `ap-northeast-2` | 동일 EPYC Genoa 3.7GHz | 램만 2배. 서울을 원하면 이것 |
| t3.micro | 아무데나 | Xeon 8259CL 2.5GHz | 무료. 시간측정 부적합(버스터블) |

- 서울↔도쿄 지연 30~40ms — SSH·배치 작업엔 체감 없음.
- ⚠️ **키페어·보안그룹은 리전별로 분리**된다. 리전을 바꾸면 새로 만들어야 하고,
  `.pem` 파일이 같은 이름으로 받아지므로 **덮어쓰지 않게 이름을 나눌 것**
  (`nypc2026.pem` = 서울 / `nypc2026-tokyo.pem` = 도쿄).
- 당일 이걸 모르면 c7a 찾다가 시간을 날린다. **`config.sh` 기본 리전은 도쿄로 설정됨.**

## 5. ⚠️ 주의

- **제출 코드는 여전히 1코어 + 시간제한.** AWS의 128코어는 *로컬 탐색·튜닝*만
  빨라지게 하지, 제출본 자체를 빠르게 만들지 않는다.
  → `skeleton.cpp` 의 단일스레드 설계는 그대로 유효.
- **LLM 규정: 동시에 하나의 에이전트만.** 원격에서 Claude를 또 띄우면 위반.
  원격은 **검증기·솔버 같은 비-LLM 프로그램**을 돌리는 용도로만.
- **이 폴더에 액세스 키를 절대 커밋하지 말 것.** 키는 `aws configure` 가
  `~/.aws/credentials` 에만 둔다. `config.sh` 에는 이름·리전만 있다.
- 대회장 WiFi가 80명 공유다. **끊길 수 있다고 가정**하고 움직일 것.
